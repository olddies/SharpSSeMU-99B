# Bringing the UI to the 0.99B look

The protocol already speaks 0.99B; the interface is still the Season 6 one. Closing that gap is the
part of the port that **cannot be done without visual judgement**: everything else is verified
against bytes and sizes, this is verified by looking.

This document exists so that whoever takes it on does not repeat the path we already walked. There
was one attempt and it was reverted; what follows is what we learned.

## First: it is not a file swap

The naive count gives hope, and is false.

The 0.99B client has 141 files in `Data/Interface`; this one has 638. Of those 141, **68 have the
same name**, which sounds like a direct replacement. But comparing contents, **64 of those 68 are
already byte-for-byte identical**: this client already ships the 0.99B asset. Only 4 really differ,
and three of those are skill icon sheets.

The 73 "that only exist in 0.99B" are not the missing ones either. Many are **renamed**: the helmet
silhouette is `Item_Cap.OZJ` in 0.99B and `newui_item_cap.OZT` here. You have to compare by role,
not by name.

And compared by role, the real difference is one of **format and size**.

## The formats

| extension | contents |
|---|---|
| `.OZJ` | 24-byte header, then a JPEG |
| `.OZT` | 4-byte header, then a TGA |

The TGA is usually 32-bit, with bit 5 of the descriptor byte saying whether the first row is the
top one.

The slot silhouettes illustrate the problem: 0.99B uses **opaque 40x40 tiles with no frame**; this
client uses **46x46 with an alpha channel and a metallic frame drawn on top**. The sizes do not match
the slot, and the frame is supplied by a different side in each version.

## The tools

Three remain in `tools/ui099b/`, with the hard part already solved:

**`compare_interface.py`** — crosses the two sets and separates those that match in name *and*
dimensions (a genuine direct swap) from those that do not. It reads the dimensions of the JPEG and
TGA inside the OZJ/OZT.

**`convert_slots.py`** — converts the slot silhouettes from one format to the other. It has
`--previsualizar` (preview), which builds a contact sheet with the result next to the current one,
over a checkerboard background so transparency is visible.

**`install_bar.py`** — installs the bottom-bar textures.

## Use the preview, seriously

The first version of `convert_slots.py` produced transparency by cutting out the JPEG's background,
because I assumed the frame came in the 0.99B image. The result was noisy with a strange border.

Zooming in on one silhouette made it clear it was the other way round: **the frame comes from this
client**, and the 0.99B one is a plain dark tile. There was nothing to cut out — the cut-out was
precisely what dirtied the image.

None of that is deducible from reading code. You see it by looking.

## Aligning textures: measure, don't eyeball

The life and mana orb textures **include fragments of the metallic ornament that surrounds them**.
That means there is exactly one position where they fit, and placing them by eye shows.

The way to find it is to compare those fragments against the background bar at every possible
position and keep the one with the smallest difference. For the mana orb this gave a mean difference
of **1.2** over 80 pixels of ornament: an exact fit. The by-eye estimates were 30 pixels off.

If a texture has edges that must continue the background, measure it this way.

## The bottom bar is not a re-skin

They are two different designs, and it is worth knowing before starting:

| | 0.99B | this client |
|---|---|---|
| height | 48 px | 51 px |
| quick keys | 3 (Q, W, E) | 4 (Q, W, E, R) plus a numbered row |
| life and mana | orbs held by claws | rectangular bars |
| button icons | **embedded in the bar** | sprites drawn on top |

That last row is a trap: if you leave the client's sprites over the 0.99B art you get **two
overlapping icons**. The buttons must become invisible click zones.

And the geometry is hand-written in `UI/NewUI/HUD/NewUIMainFrameWindow.cpp`: positions, widths and
heights as literal numbers. Changing the art without changing those numbers leaves everything shifted.

The decision to make first is whether the port is faithful — three keys, losing R and the numbered
shortcuts — or keeps the features and accepts a mixed aesthetic. We tried the faithful route and the
result was not convincing; with more visual iteration it might be.

## The order we recommend

1. **Empty equipment slots** (11 textures). Self-contained, no layout changes.
2. **Shop buttons** (`buy`, `sell`, `repair`, `coin`, `Money_*`).
3. **Chat window frame** (`nis_*`).
4. **NPC dialog** (13 files). Already requires rewriting positions.
5. **Bottom bar**. The most visible and the one that demands the most decisions.

## Before touching anything

`src/bin/Data/Interface` is the source; the build copies from there. Make a copy of the whole folder
before starting — the tools make one on their own in `Interface.s6` the first time.

When restoring, copy with a new timestamp: if you preserve the original one, CMake does not consider
the files modified and the build keeps the old ones. It happened to us.
